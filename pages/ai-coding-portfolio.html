Building My Portfolio in Code

I built this portfolio in HTML, CSS, and JavaScript with AI coding tools. Working in the browser let me test responsive layouts and keyboard interactions as I designed, while keeping the implementation under my control.

My role

End-to-end: UX, UI, front-end architecture, and AI-assisted engineering. I designed the system, wrote the code, and built the workflow.

Key outcomes

  • Fully custom site built without templates or CMS
  • Reusable UI + code patterns across all case studies
  • AI assistant connected to project notes

At a glance

  • The Goal: I wanted to build the entire site in code to sharpen my UX engineering workflow, test layout behavior and keyboard navigation under real rendering conditions, and ship without a frontend bottleneck.
  • How I Built It: Wrote custom semantic HTML and modular CSS with Cursor, avoiding bloated templates and heavy frontend frameworks. I built a serverless backend with Supabase and pgvector so the assistant retrieves targeted project notes on demand.
  • The Result: The result is a custom portfolio with shared design tokens, reusable page patterns, and an assistant connected to my project notes. Building it also gave me a practical workflow for testing interface ideas in code.

Problem

I do my best work when I'm close to the implementation. Sitting between design and engineering helps me spot technical constraints early, speak the same language as our developers, and avoid designing interactions that are difficult to maintain in production.

I wanted to test modern AI-assisted engineering tools on a real project, so I built this portfolio from scratch in code instead of using an off-the-shelf template.

What I set out to do

  • Move directly from an interaction idea into working code in a few hours
  • Create a clean token hierarchy that keeps styles modular across multiple pages
  • Build an AI chat assistant connected to relevant project notes
  • Keep the site lightweight, semantic, and keyboard accessible

Approach

I treated the code like a production design system. I set up design tokens for spacing and type first, locked in modular layout grids, and tested components directly in Chrome.

  • Cursor & Claude Code: Coding environments for writing semantic markup, styling tokens, and frontend scripts
  • Vercel & Supabase: Serverless deployment, vector search, and edge caching

The biggest takeaway was that AI tools are only as good as the guardrails you give them. When you establish clear tokens and layout rules upfront, AI accelerates boilerplate markup and produces clean, maintainable styles.

Building the system

Designing directly in the browser

Figma is great for team alignment, but jumping straight into HTML and CSS cut out an entire layer of translation lag. I could resize my browser window, test keyboard navigation, and check contrast under real rendering conditions, catching layout quirks before they reached production.

Setting ground rules before writing code

If you do not give an AI coding tool strict rules, it will happily invent new CSS classes on every prompt and pad your copy with corporate fluff. Before writing code, I set up explicit project guidelines in local markdown files (CONTEXT.md and AGENTS.md). These defined my tone preferences, banned resume buzzwords, and set hard standards for keyboard accessibility and semantic HTML.

Keeping the CSS modular

The fastest way for an AI-assisted codebase to turn into an unmaintainable mess is letting it write styling rules wherever it wants. I split the stylesheets into clear layers: tokens for colors and spacing, base styles for typography, layout files for grids, and component files for interactive widgets (tokens.css, base.css, layout.css, components.css, pages.css). That kept our CSS clean, prevented styling collisions, and made stylesheets straightforward to maintain.

Implementation highlights

  • A consistent case study template that lets readers scan decisions quickly
  • Reusable layout patterns and components across every page
  • An AI chat widget connected to semantic search for hiring managers who want quick answers
  • Semantic HTML, ARIA landmarks, and SEO metadata baked directly into the templates

The result was a fast, accessible portfolio built with the same discipline and durability as a production software application.

Making the AI Assistant Useful

The first version of my portfolio assistant passed an entire 40KB JSON file on every API call. It was quick to build, but wildly inefficient. It blew past token limits whenever someone asked a detailed question about past project metrics.

To fix that token limit problem, I broke my case study notes into structured chunks and stored them in Supabase using vector search. Now, when a recruiter or hiring manager asks a specific question (like how I approached design tokens or why we pushed back on an AI-first dashboard), the endpoint retrieves only the relevant excerpts before streaming a grounded response with Gemini without stalling the UI.

To keep the bot honest, I wrote 61 automated Vitest tests covering edge cases, role fit, and metric accuracy. If someone asks something outside my background, the assistant politely declines instead of making up answers. Building this gave me firsthand appreciation for the latency and prompt guardrails our engineering teams deal with every day.

Tradeoff

Setting up vector search and test guardrails took extra time upfront. But it turned a generic chatbot into a grounded tool that actually reflects how I work.

Impact

Building the portfolio in production code shortened the back-and-forth between designing an interaction and seeing how it actually behaves. Prototyping directly in the browser exposed edge-case layout breaks, font-rendering quirks, and accessibility barriers that static Figma canvases conceal.

The biggest advantage is speed. When I want to test an interaction idea, I can build a working prototype in an afternoon, test it on a phone, and make sure keyboard navigation and responsive layouts feel solid before handing specifications to developers.

What Didn't Work

Early on, I went down a rabbit hole building multiple visual skins, including a dark mode and a retro Windows 95 theme (alongside the terminal mode). While they were fun technical experiments, maintaining three separate color palettes and border conventions tripled CSS token maintenance and distracted from the case studies themselves.

I stripped the site back to a single high-contrast light theme to keep the design system maintainable and focused on content clarity. The lesson was straightforward: just because AI makes generating code fast doesn't mean you should keep every feature you prototype.

Lessons & Next Steps

Lessons

AI coding tools do not replace good software practices. If anything, they punish you faster if you do not have a plan. Without clear architecture upfront, an LLM will happily hand you messy CSS and duplicate utility classes.

  • Detailed system rules beat prompt hacking: Setting up explicit coding conventions and design tokens in markdown prevented messy rewrites later.
  • Browser testing catches real-world friction: Inspecting live HTML and CSS revealed keyboard navigation quirks and awkward responsive wrapping that Figma never surfaced.
  • Fast prototyping requires discipline: When coding is quick, it's easy to build unnecessary features (like the retro themes I ended up cutting). Knowing what to prune is the real job.
